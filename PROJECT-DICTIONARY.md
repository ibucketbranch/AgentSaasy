# AgentSaasy Project Dictionary

> **Quick reference guide for AI agent terminology used in this project.**

---

## Core Agentic AI & General Terms

### Agentic AI / Agentic Agents
AI systems with **agency**—they autonomously pursue goals by perceiving, reasoning, 
planning, using tools, acting, and adapting (often in loops). "Agentic agents" is 
a common (slightly redundant) way people emphasize the autonomous, proactive nature. 
Differs from pure generative AI (which just outputs text/images).

### AI Agent
An autonomous software entity powered by an LLM that can reason, use tools, remember 
context, and execute multi-step tasks toward a goal (e.g., your data analysis agent).

### ReAct (Reason + Act)
A popular agent loop pattern: The agent alternates between **reasoning** (thinking 
step-by-step about what to do next) and **acting** (calling a tool or taking an 
action), then observes the result and repeats until the task is complete. This is 
what powers most simple agents like the one in your LangChain prototype.

**Pattern:**
```
Thought → Action → Observation → Thought → Action → ... → Final Answer
```

### Chain-of-Thought (CoT)
A prompting technique where the LLM is instructed to "think step by step" before 
answering. Used heavily in the Reasoning Layer to improve planning and decision 
quality.

### Tool Calling / Function Calling
The mechanism where an LLM decides to invoke an external function/tool (e.g., 
`query_data` or `clean_data` in your agent) instead of just generating text. The 
model outputs a structured call (like JSON), the framework executes it, and feeds 
the result back.

**Example:**
```python
@tool
def query_data(query: str) -> str:
    """Query sales data by product, region, or date."""
    # Tool implementation
```

**Cost consideration:** Each tool call = 1 LLM round trip = 1 API request. A query 
requiring 3 tool calls = 3 separate API requests. Optimize by combining related 
operations into single tools or reducing `max_iterations`.

### Orchestration
The control layer that manages the overall workflow: deciding when to reason, call 
tools, loop, handle errors, or stop. In simple agents it's often a ReAct loop; in 
advanced ones it's graph-based (e.g., LangGraph).

### Memory
How agents retain context across interactions.

- **Short-term memory**: Conversation history or current task state (e.g., 
  `ConversationBufferMemory` in LangChain)
- **Long-term memory**: Persistent storage like vector databases for past analyses 
  or user preferences

### Vector Store / Vector Database
A database (e.g., Chroma, Pinecone, Weaviate) that stores **embeddings** (numerical 
representations of text/data) for fast semantic search/retrieval. Often used for 
RAG or long-term memory in agents.

### RAG (Retrieval-Augmented Generation)
Pattern where agents retrieve relevant documents/data before generating answers. 
Instead of relying solely on the LLM's training data, the agent first searches a 
knowledge base (often a vector store) for relevant information, then uses that 
context to generate a more accurate, grounded response.

**Use case:** When your agent needs to reference historical reports, company 
documents, or external knowledge not in the LLM's training data.

**Example flow:**
```
User Query → Retrieve relevant docs → Pass to LLM with context → Generate answer
```

### Embedding
Converting text into numerical vectors (arrays of numbers) that capture semantic 
meaning. Similar concepts have similar embeddings, enabling semantic search. 
Generated by specialized models (e.g., OpenAI's `text-embedding-ada-002`).

**Example:**
```python
"sales report" → [0.23, -0.45, 0.67, ...] (1536 dimensions)
"revenue analysis" → [0.25, -0.43, 0.65, ...] (similar vector)
```

### Token
The unit of text an LLM processes (roughly ¾ of a word in English). Important for 
understanding API costs and context limits. 

**Examples:**
- "Hello world" ≈ 2 tokens
- "AgentSaasy" ≈ 3 tokens (Age-nt-Saasy)
- 1,000 words ≈ 1,333 tokens

**Why it matters:** API pricing is per token, not per word.

### Context Window
Maximum amount of text (in tokens) an LLM can process at once. This includes your 
prompt, conversation history, tool outputs, and the response.

**Model limits:**
- GPT-4o-mini: 128k tokens (~96k words)
- GPT-4o: 128k tokens
- Claude Sonnet 4: 200k tokens

**Practical impact:** If your agent's conversation + tool outputs exceed the limit, 
older messages get truncated.

## LangChain-Specific Terms

> Relevant to your 3-layer agent prototype

> ⚠️ **Version Note**: This project uses **LangChain 0.1.0**. Some APIs differ 
> in 0.2.x+ (e.g., imports moved, new patterns introduced). Stick with 0.1.x 
> for now to avoid breaking changes.

### LangChain
An open-source Python/JS framework for building LLM-powered applications. It provides 
building blocks like prompts, chains, agents, tools, memory, and integrations. Your 
3-layer agent uses it for easy tool calling and ReAct orchestration.

**Website:** https://langchain.com

### Chain
A fixed, sequential workflow in LangChain (e.g., prompt → LLM → output parser). 
Simpler than agents—good for predictable flows, but less flexible than dynamic agents.

**When to use Chain vs ReAct Agent:**
- ✅ **Use Chain**: When workflow is fixed and predictable (e.g., always: 
  clean data → analyze → generate report)
- ✅ **Use ReAct Agent**: When you don't know steps ahead of time, need dynamic 
  tool selection based on input (e.g., user asks varied questions requiring 
  different tools)

### Agent (in LangChain)
A dynamic executor that uses an LLM as a **reasoning engine** to choose actions/tools 
at runtime. Your prototype uses `create_react_agent` + `AgentExecutor`—this is the 
orchestration glue.

**Key difference from Chain:** Agent decides what to do next; Chain follows a script.

### Tool
A function wrapped with metadata (name, description, args schema) so the LLM knows 
when/how to call it. Defined with `@tool` decorator in your code.

**Your tools:**
- `query_data` - Filter and retrieve sales data
- `analyze_trends` - Calculate growth rates and patterns
- `detect_anomalies` - Find outliers in data

### AgentExecutor
The runtime that runs the agent loop: feeds input to the agent, handles tool 
execution, manages memory, retries errors, and returns final output. Set 
`verbose=True` to see the full thinking trace.

**Configuration options:**
- `max_iterations` - Prevent infinite loops
- `handle_parsing_errors` - Gracefully handle malformed tool calls
- `verbose` - Show reasoning steps (useful for debugging)

### Prompt Template
Reusable string templates with placeholders (e.g., for instructions or examples) 
that get filled at runtime.

**Example:**
```python
template = "You are a {role}. Answer: {question}"
prompt = PromptTemplate(template=template, input_variables=["role", "question"])
```

## Related Frameworks

> Mentioned for future scaling

### LangGraph
An extension of LangChain for building more complex, stateful, **graph-based** 
agents/workflows. Supports loops, branching, multi-agent coordination, and 
persistence—ideal when your simple 3-layer agent needs to grow enterprise-grade.

**Use when:**
- You need conditional branching (if/else logic)
- Multiple agents need to collaborate
- State needs to persist across sessions
- Complex error recovery is required

**Website:** https://langchain-ai.github.io/langgraph/

### CrewAI
A higher-level framework for **multi-agent "crews"** where agents have roles, 
delegate tasks, and collaborate. Great for team-like orchestration (e.g., one 
agent cleans data, another analyzes, a third reports).

**Use when:**
- You want agents with distinct roles (Manager, Analyst, Researcher)
- Tasks need to be delegated between agents
- You prefer a higher-level abstraction than LangGraph

**Website:** https://crewai.com

**Tool design tips:**
- Keep docstrings clear—the LLM reads them to decide when to call
- Include examples in docstrings (helps LLM understand usage)
- Return strings, not objects (easier for LLM to interpret)
- Handle errors gracefully (return error message as string)

## Common Issues & Troubleshooting

### Agent Loops Infinitely
**Symptoms:** Agent keeps calling tools repeatedly, never reaches "Final Answer"

**Causes:**
- Tool returns unclear/ambiguous results
- Tool fails but doesn't return clear error message
- Agent doesn't understand when task is complete

**Fixes:**
```python
# 1. Set max_iterations to prevent runaway
agent = AgentExecutor(agent=agent, tools=tools, max_iterations=5)

# 2. Improve tool return messages
return f"Found {len(results)} records. Summary: {summary}"  # Clear
# Not: return str(results)  # Ambiguous

# 3. Add explicit completion signals in prompt
"When you have enough information, provide Final Answer immediately."
```

### Tool Not Being Called
**Symptoms:** Agent responds with text instead of using available tools

**Causes:**
- Tool docstring unclear or missing examples
- Tool name doesn't match what LLM expects
- Query doesn't clearly match tool's purpose

**Fixes:**
```python
# Bad docstring
@tool
def query_data(query: str) -> str:
    """Query data."""  # Too vague!

# Good docstring
@tool
def query_data(query: str) -> str:
    """Query sales data. Use for filtering by product, region, date range, 
    or quarter. Examples: 'last quarter', 'Widget A', 'North region', 'Q1 2024'.
    """
```

### Out of Context / Token Limit Exceeded
**Symptoms:** Error about context length, or agent "forgets" earlier conversation

**Causes:**
- Too many tool calls with large outputs
- Conversation history too long
- Data returned by tools is too verbose

**Fixes:**
```python
# 1. Summarize tool outputs
return df.head(10).to_string()  # Not entire dataset

# 2. Use memory with token limits
memory = ConversationBufferWindowMemory(k=5)  # Keep last 5 exchanges

# 3. Clear memory between unrelated queries
agent.memory.clear()
```

### Parsing Errors / Malformed Tool Calls
**Symptoms:** `OutputParserException`, agent can't parse its own output

**Causes:**
- LLM generates invalid JSON for tool call
- Response format doesn't match expected pattern

**Fixes:**
```python
# Enable error handling in AgentExecutor
agent = AgentExecutor(
    agent=agent,
    tools=tools,
    handle_parsing_errors=True,  # Retry on parse errors
    verbose=True,  # See what went wrong
)
```

### High API Costs
**Symptoms:** Unexpected API bills, costs higher than estimated

**Causes:**
- Too many iterations per query
- Large data being passed in tool outputs
- Using expensive models unnecessarily

**Fixes:**
```python
# 1. Use cheaper model for simple tasks
llm = ChatOpenAI(model="gpt-4o-mini")  # Not gpt-4o

# 2. Limit iterations
max_iterations=3  # Enough for most queries

# 3. Summarize data before returning
return f"Analyzed {len(df)} rows. Top insight: {insight}"
# Not: return df.to_string()  # Wastes tokens
```

## Cost & Performance Considerations

### API Pricing (as of Feb 2026)

**OpenAI GPT-4o-mini** (used in this project):
- Input: $0.15 per 1M tokens
- Output: $0.60 per 1M tokens
- **Typical agent query:** ~2,000 input + 500 output tokens = **$0.0006**

**Typical usage costs:**
| Activity | Tokens | Cost (GPT-4o-mini) |
|----------|--------|-------------------|
| Single query (1 tool call) | ~2,500 | $0.0004 |
| Complex query (3 tool calls) | ~6,000 | $0.0012 |
| 100 test queries | ~250k | $0.06 |
| 1,000 production queries | ~2.5M | $0.60 |

### Performance Optimization Tips

**Reduce latency:**
- Use streaming responses for better UX
- Cache frequent queries (e.g., "What's last quarter's total?")
- Batch similar queries when possible

**Reduce costs:**
- Limit `max_iterations` (fewer tool calls = lower cost)
- Summarize data before returning from tools
- Use `gpt-4o-mini` instead of `gpt-4o` (20x cheaper)
- Clear memory between unrelated conversations

**Improve accuracy:**
- Provide clear, detailed tool docstrings with examples
- Use Chain-of-Thought prompting in system message
- Test with `verbose=True` to debug reasoning
- Add few-shot examples to prompt for complex tasks
