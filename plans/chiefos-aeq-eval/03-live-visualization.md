# ChiefOS Live Visualization Pipeline - Design

**Written 2026-08-16. Status: DESIGN. Companion to `README.md` in this directory.**

## 0. Summary of the recommendation

- Transport, primary: the Mac mini pushes sanitized events to Supabase (Postgres + Storage + Realtime) via an authenticated Edge Function. The browser reads via the anon key: snapshot fetch first, Realtime subscription for live mode. The static site stays static; the data plane lives entirely off-site.
- Transport, fallback (always shipped, not optional): committed sanitized recordings of real cycles baked into the site at build time, played back at true pace under a "RECORDED RUN - REAL DATA" badge. This is also v0, shippable in days.
- Page: a new page `/projects/chiefos-live/`, copy-adapting the agentsaasy canvas engine with a ChiefOS topology. `agentsaasy.astro` stays untouched and keeps its SIMULATED badge; `chiefos.astro` gets only a small status chip linking to the live page.
- Honesty model: a badge state machine (LIVE / CONNECTED-IDLE / SNAPSHOT / RECORDED) with explicit truth conditions; states degrade downward, never upward. The SIMULATED state only ever appears on the AgentSaaSy demo.

## 1. Transport architecture

### 1.1 Decision: Supabase primary, committed recordings fallback

Primary: the mini POSTs events over HTTPS to a Supabase Edge Function (`ingest`); the function validates and inserts into Postgres; the page reads a public snapshot and subscribes to Realtime with the anon key.

Rationale, in order of weight:

1. NAT fit. The mini is push-only behind home NAT. Supabase needs nothing inbound; outbound HTTPS is the whole story.
2. Governance fit rules out a VPS relay. A relay service on the site's VPS requires editing nginx config on a box shared with the njoy stack; the website session's settings deny state-changing operations against the VPS, and a relay is a new always-on process to operate and secure on a machine where a mistake takes down a second live service. Supabase already exists in the stack, costs nothing at this volume, and moves the entire dynamic surface off the box that serves the site.
3. Static purity is preserved literally. The site's "Nothing runs at request time" claim stays true of the site. The page ships as static HTML with a client-side island talking to an external data plane - the same pattern as the existing analytics beacon. No adapter, no API routes, no build-time coupling to live data.
4. Cost. An hourly cycle emitting a few hundred events is ~5-10k rows/day; free tier covers Postgres, Storage, Edge Functions, and Realtime (200 concurrent connections, far above portfolio-site traffic). If Realtime connections were exhausted, the page silently stays in snapshot-polling mode, which is already the v1 behavior.
5. Read-side security is solved there: RLS gives read-only public access on exactly the intended tables; the anon key is designed for public exposure.

Fallback: committed recordings. One or more real, sanitized, hand-approved cycle recordings live in the website repo (`src/data/chiefos/recordings/`). The page always ships with one. Every runtime failure (Supabase unreachable, snapshot stale, schema version unknown, JS blocked) lands on the recording, labeled honestly. The page's worst case is identical to its v0; the site never depends on the mini being awake.

Why not periodic static snapshot into the site as primary: pushing a snapshot into the site means either hourly commits (deploy churn, and it violates "upstream never touches the website repo") or hourly rsync from the mini to the production docroot (a write credential on the mini that can touch the live site - a much worse blast radius than a Supabase insert token). The good half of the idea is absorbed: the snapshot is a Supabase Storage object.

### 1.2 Write path and security

- On the mini (ChiefOS side): a small emitter module buffers events per cycle and POSTs batches (end of each task, plus cycle end, plus a 5-minute heartbeat) to the `ingest` Edge Function with a bearer secret. Retries with backoff; drops silently after the buffer cap (telemetry must never block or crash the swarm). The secret lives in the mini's keychain/env, never in any repo.
- Edge Function `ingest`: checks the bearer secret; validates against the versioned schema (section 3); enforces sanitization structurally - every field is a number, enum, or ID from the closed vocabulary, and there are no free-text fields at all, so a path, table name, port, or prompt cannot leak even by bug (the do-not-publish list enforced by type, not regex). Inserts with the service role. Rejects unknown schema majors.
- Read path: RLS on `swarm_events` and `swarm_cycles`: SELECT for anon, nothing else. Realtime enabled on `swarm_events` inserts. Snapshot object `swarm/snapshot.json` in a public Storage bucket, regenerated by the Edge Function whenever it ingests a `cycle_completed` event.
- Naming discipline: these Supabase tables are new public infrastructure, not ChiefOS's internal schema; keep names generic (`swarm_events`, `swarm_cycles`) and deliberately unrelated to any internal ChiefOS table name.
- Retention (pg_cron): raw events 30 days; cycle summaries indefinitely (long-run chart material); snapshot holds the last 24h plus the latest full cycle.

### 1.3 The LIVE badge: truth conditions and the burstiness problem

The swarm runs hourly, so a random visitor almost always arrives between cycles. Principle: the default experience is a replay of the latest real cycle; "live" is a bonus state the page promotes itself into, never a promise.

| State | Badge | Truth conditions |
|---|---|---|
| LIVE | LIVE - REAL DATA (pulsing dot) | Realtime connected AND a cycle_started received without its cycle_completed AND last event age < 120 s |
| LIVE-IDLE | CONNECTED - SWARM IDLE (steady dot) | Realtime connected AND last heartbeat < 10 min AND no cycle in progress. Canvas replays the latest completed cycle with the caption "Replaying last completed cycle (HH:MM UTC). Swarm is between cycles." |
| SNAPSHOT | LATEST CYCLE - REAL DATA (as of HH:MM) | Realtime unavailable but snapshot fetch succeeded and generated_at < 24 h |
| RECORDED | RECORDED RUN - REAL DATA (YYYY-MM-DD) | Everything else: fetch failed, data stale, schema unknown, mini offline for a day |

Transitions only announce themselves downward ("connection lost, showing last snapshot") in the harness log; upward transitions swap silently mid-idle. The hourly cadence is already public on the ChiefOS page, so "next cycle expected around HH:MM" is publishable; the exact minute-of-hour is not shown.

Replay pacing: real cycles have long quiet stretches, so replay defaults to compressed time with an explicit label ("replay at 60x, timestamps real") and offers a 1x toggle. Compression is labeled, so it stays inside the integrity rules: the data is real, the clock is declared.

### 1.4 Failure modes

| Failure | Behavior |
|---|---|
| Mini offline | Heartbeats stop; page drops LIVE-IDLE -> SNAPSHOT after 10 min; -> RECORDED after snapshot ages past 24 h. No error state beyond honest badges. |
| Supabase down | Snapshot and Realtime both fail; page boots straight into RECORDED from the committed file. |
| Schema version bump | Page checks `v`; unknown major -> RECORDED (the committed recording always matches the shipped player). |
| Emitter bug floods events | Edge Function rate-limits per cycle; page caps its render queue. |
| Token leak from the mini | Worst case: someone can insert fake telemetry rows. They cannot read anything private (nothing private is in the tables) or touch the site. Rotate the secret in the Edge Function config. |

Infra note to verify at build time: if nginx sets a Content-Security-Policy header for the site, connect-src must include the Supabase project domain and its wss: endpoint. Check the VPS nginx config read-only before shipping v1.

## 2. Page and UX design

### 2.1 Where it lives: new page `/projects/chiefos-live/`

- Not wired into agentsaasy.astro. That page is a demo of a different project and its SIMULATED badge is load-bearing for the site's integrity story. It stays exactly as is, permanently simulated; its simulated threshold boot-log line stays inside the simulation.
- Not embedded in chiefos.astro. That page is polished CSS-only editorial content with an "In Production" claim; bolting a supabase-js island and a heavy canvas onto it changes its character and doubles its failure surface. It gets one small addition: a static status chip in the hero ("See the swarm run: live telemetry ->") linking to the new page. No fetch.
- New page: `src/pages/projects/chiefos-live.astro`, titled along the lines of "ChiefOS: The Swarm, Observed". Copy-adapt the agentsaasy engine (~250 lines, already data-driven via NODES/EDGES/STAGES) rather than extracting a shared module: a shared module would put the existing published page in the blast radius of every live-page change on a repo that deploys to production in 2 minutes. Duplication is the cheaper risk.

EDGES: intake -> orchestrator; orchestrator to and from each specialist; each LLM-using specialist to the tier nodes; the fallback chain tier_rules -> tier_fast -> tier_analyst -> tier_cloud drawn as a distinct dashed vertical rail (escalation animates a packet climbing it); specialists -> review and -> filed.

STAGES: replaced by an event-driven EVENT_MAP - the key engine change. The demo advances a job through a fixed STAGES array on a timer; the live page instead consumes a time-ordered event list (from Realtime, snapshot, or recording - one interface, three sources) and maps each event type to {hops, pulse, logLine(event)}. E.g. llm_call{tier:'cloud', outcome:'escalated'} -> hop specialist -> tier rail with the climb animation; task_completed{review_queued>0} -> hops to review. Log lines are generated client-side from structured fields only ("filing_clerk: 12 docs classified, 2 to review, local_fast"), so no upstream string ever reaches the DOM.

### 2.3 Side-panel meters

1. AEQ-L card - "Latest evaluated AEQ-L" with the score, the gate verdict chip (GREEN/YELLOW/RED), and "evaluated YYYY-MM-DD, pre-registered protocol". Batch data from the latest eval_published event, explicitly labeled as an evaluation result, not a live meter. No threshold numbers anywhere (section 4).
2. Tokens this cycle - running counter, plus per-cycle total in replay.
3. Tier distribution - horizontal stacked bar: rules / local fast / local analyst / cloud, by call count, token share on hover. The page's thesis-carrying meter: local-first economics made visible.
4. Review-queue rate - items queued for human review / items processed this cycle. The honesty meter: the swarm asks instead of guessing.
5. Coordination overhead - orchestrator + routing tokens as a share of total cycle tokens.
6. Cycle counters - docs processed, cycle duration, cycles in last 24 h (from snapshot history).

Badge placement mirrors the demo's .sim-badge position; the states get distinct colors (LIVE pulsing green, SNAPSHOT/RECORDED amber; the SIMULATED style stays unique to agentsaasy). Footer disclaimer text mirrors the badge state.

## 3. Data contract (v1)

One envelope, three carriers (Realtime insert payload, snapshot event arrays, committed recording files). The telemetry workstream owns the emitter; this shape is the interface.

```json
{ "v": 1, "seq": 4821, "ts": "2026-08-16T14:03:22.114Z",
  "cycle_id": "c-20260816-14", "type": "llm_call", "data": { } }
```

Closed vocabularies: agent in {orchestrator, filing_clerk, lost_found, dedup_hunter, student, profiler, auditor, keeper}; tier in {rules, local_fast, local_analyst, cloud}; task_kind in {classify, file, rescue, dedup_scan, profile, learn, audit, healthcheck}; outcome in {accepted, escalated, review}. Every data field is a number or one of these enums. No strings otherwise, no IDs derived from document content, counts only.

Event types:

| type | data |
|---|---|
| cycle_started | { planned_agents: [agent...] } |
| agent_task_started | { agent, task_kind, doc_count } |
| llm_call | { agent, tier, tokens_in, tokens_out, latency_ms, outcome } |
| task_completed | { agent, task_kind, items_done, review_queued } |
| cycle_completed | { docs_processed, duration_s, tokens_total, tokens_by_tier: {...}, calls_by_tier: {...}, review_queue_added, coordination_tokens } |
| eval_published | { run_id_hash, aeq_l, verdict: "green"|"yellow"|"red", evaluated_at } |
| heartbeat | {} |

Snapshot swarm/snapshot.json:

```json
{ "v": 1, "generated_at": "...",
  "status": { "last_heartbeat": "...", "cycle_in_progress": false },
  "latest_eval": { "aeq_l": 0.0, "verdict": "green", "evaluated_at": "..." },
  "cycles": [ "last 24 cycle_completed.data records, newest first" ],
  "latest_cycle_events": [ "full envelope array for the newest completed cycle" ] }
```

Recording files (v0): src/data/chiefos/recordings/cycle-YYYYMMDD.json = { v, provenance: { recorded_at, source: "ChiefOS production, sanitized", approved: "YYYY-MM-DD" }, events: [envelopes] }. Same event shape, so the player is one implementation.

Versioning: v is a major; the page hard-checks it and falls back to RECORDED on mismatch. Additive fields allowed within a major; the player ignores unknown keys. Emitter, Edge Function validator, and page player all pin the same v.

## 4. Governance-compliant delivery

Who does what (per the coordination contract, nobody upstream touches the website repo):

- The coordinating session delivers this design to both sides and, holding Supabase access, can provision the data plane when asked: tables, RLS, pg_cron retention, Storage bucket, Edge Function. The ingest secret is generated and handed to the operator out-of-band for the mini; it never enters any repo. The website repo eventually carries only the project URL and anon key (designed-public).
- The ChiefOS session builds the emitter + sanitizer in its own tree, exports the v0 recording, and queues delivery per the contract: an entry in its prompts/website-publish-queue.json (schema 2, kind "project", source pointing at the sanitized recording JSON and a short copy block, repo-relative paths) plus a message to the website session - the contract is explicit that queueing alone is not the trigger. The recording is pre-scrubbed against the do-not-publish list before queueing; the structural no-strings contract makes that scrub a type check.
- The website session builds chiefos-live.astro, the player, the badge machine, the chiefos.astro status chip; imports the recording; runs the build gate; sets the queue entry to published. Per contract lesson 7, the recording import gets an assertion (event count + schema version echoed at build) so a silently empty recording fails the build instead of shipping a dead canvas.

The threshold reconciliation. Three facts held simultaneously: (1) the demo's GREEN >= 0.90 / YELLOW >= 0.50 are simulated demo values and stay only on the agentsaasy page inside the SIMULATED frame; (2) real gate thresholds are pre-registered and are on the ChiefOS do-not-publish list; (3) published claims must be real. Resolution: the live page shows verdicts, never thresholds. The emitter sends verdict as an enum computed on the mini; the numeric AEQ-L score is publishable (a result, not a threshold), the cut lines are not, and the page says so in one sentence: "Verdicts follow thresholds pre-registered before the run; the thresholds themselves are not published." That sentence is a new connective claim, so per contract lesson 6 it must be verified against the pre-registration doc by the ChiefOS session before it ships. The demo's boot-log line quoting thresholds must not be copy-adapted into the new page.

House style throughout: plain ASCII, straight quotes, no em dashes (build gate enforces), no banned phrasing in new copy, state what it does without positioning.

## 5. Phasing and effort

**v0 - recorded real cycle (days).** ChiefOS: emitter events to local JSONL, one cycle exported, sanitized, approved, queued (0.5-1 day). Website: new page, copy-adapted engine with EVENT_MAP player, ChiefOS topology, meters computed from the event list, RECORDED badge, 1x/60x toggle, chiefos.astro chip (1-1.5 days). No Supabase dependency. Total ~2-2.5 days across sessions.

**v1 - auto-updating snapshot (next 1-2 weeks).** Provision Supabase (tables, RLS, ingest function, storage, retention cron): 0.5 day. ChiefOS: point the emitter at ingest, add heartbeat: 0.5 day. Website: snapshot fetch + SNAPSHOT badge + staleness fallback to the committed recording; verify nginx CSP allows the Supabase origin: 0.5-1 day. Total ~1.5-2 days.

**v2 - true realtime.** Website mostly: supabase-js Realtime subscription, LIVE / LIVE-IDLE states, live event feed into the same player, reconnect handling: 1-1.5 days. ChiefOS: batch-flush tuning so hops animate promptly (flush per event during a cycle, not per task): 0.5 day.

Each phase is independently honest: v0 ships "RECORDED RUN - REAL DATA" with no infrastructure, and nothing in v1/v2 can fail in a way that leaves the page worse than v0.
